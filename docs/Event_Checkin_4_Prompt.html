React Native + Expo

CONTESTO DELL’ESPERIMENTO
Realizza da zero "Event Check-in", una piccola app per il controllo accessi a un meetup. Questa è una delle 4 implementazioni confrontate in un talk tecnico: il comportamento e i dati devono essere IDENTICI nelle quattro versioni. Priorità assoluta ad Android/iOS. Prepara una base che consenta una futura estensione al Web, ma non sacrificare la demo mobile.

SPECIFICA FUNZIONALE INVARIANTE
- Un unico evento: "Tech Meetup 2026", data 23/10/2026; interfaccia in italiano.
- Partecipanti iniziali: {id:"EVT-001",name:"Giulia Rossi"}, {id:"EVT-002",name:"Marco Bianchi"}, {id:"EVT-003",name:"Sara De Luca"}, {id:"EVT-004",name:"Davide Greco"}, {id:"EVT-005",name:"Fabio Conti"}, {id:"EVT-006",name:"Ivan Moretti"}. Nessuno inizialmente registrato.
- QR di prova: il contenuto è ESATTAMENTE l’ID, per esempio EVT-001. Nessun URL, token o JSON: non cambiare lo schema.
- Una schermata con titolo evento, contatore "X / 6 presenti", ricerca per nome/ID, elenco con nominativo, ID e stato (In attesa/Presente), pulsante "Scansiona QR" e un piccolo modulo per inserimento manuale del codice (indispensabile per simulatori o permessi negati).
- Scansione QR dalla fotocamera con richiesta dei permessi e gestione di rifiuto, assenza camera o scanner non supportato. L'inserimento manuale DEVE funzionare indipendentemente dalla camera.
- Quando arriva un ID valido non ancora registrato: segna check-in, mostra conferma visibile e aggiorna contatore. Se già presente: messaggio "Check-in già effettuato" senza incremento. ID sconosciuto: messaggio "QR non valido". Ignora spazi prima/dopo. Blocca scansioni duplicate nello stesso secondo.
- Salva solo lo stato dei check-in in storage LOCALE; al riavvio mantieni gli stati. Tasto "Reimposta demo" con conferma che azzera lo stato. Nessun server, login, analytics, API remote, AI dentro l'app o database cloud.
- Layout sobrio e coerente: sfondo chiaro, accento verde petrolio #25785B, card, righe leggibili; area touch comoda; adattamento sensato ai vari schermi. Accessibilità: etichette dei pulsanti, stato testuale, contrasto e focus/tastiera dove applicabile.

ARCHITETTURA E CONSEGNA
- Separa modelli, dati seed, logica check-in, storage, componente schermata e implementazione scanner. Una funzione pura processCheckIn(id, participants) restituisce un esito tipizzato, da testare senza UI.
- Niente pseudocodice, TODO fittizi o dipendenze inventate. Crea realmente tutti i file, manifest, permessi e configurazioni richieste nel repository; se non hai accesso al file system, fornisci struttura e contenuto COMPLETO dei file.
- Usa versioni stabili effettivamente compatibili alla data di esecuzione; prima verifica documentazione e requisiti SDK. Non inventare numeri di versione o API. Evita dipendenze superflue.
- Produci README con requisiti, comandi per installare, avviare su Android e iOS, concedere permessi, build/release e limiti noti. Esponi chiaramente ciò che non è stato eseguito o compilato: non dichiarare test superati senza averli eseguiti.
- Implementa test automatici della funzione di check-in: valido, duplicato, sconosciuto, trim del codice; e un test della persistenza se praticabile.
- Al termine dai un resoconto STANDARD per il confronto: framework/versioni, librerie principali, numero file e dipendenze dirette aggiunte, comandi build, target verificati realmente, errori e correzioni manuali, sezioni specifiche di piattaforma, possibilità Web e criticità Desktop. Se hai accesso al terminale, esegui comandi e test e riporta output sintetico; se non puoi, indica NON VERIFICATO.

CRITERI DI ACCETTAZIONE
1) Prima apertura: 0/6; 2) inserisco EVT-001: 1/6 e Giulia Presente; 3) ripeto EVT-001: resta 1/6; 4) inserisco ERR-999: resta 1/6; 5) chiudo e riapro: resta 1/6; 6) reset: torna 0/6; 7) su dispositivo reale scanner legge un QR che contiene EVT-002. Il test 7 non deve impedire di usare la demo quando camera non disponibile.

MODALITÀ DI LAVORO
Non fermarti a una spiegazione o a uno scheletro di codice: implementa il progetto. Quando una dipendenza non è compatibile, scegli un'alternativa verificata e documenta il compromesso senza cambiare il comportamento. Non affermare che Android, iOS, Web o Desktop funzionino se non hai prodotto/verificato i rispettivi target.

STACK RICHIESTO: React Native + Expo, TypeScript rigoroso. Parti da create-expo-app con template TypeScript e usa il workflow Expo supportato, preferibilmente Expo Router soltanto se serve realmente; per una sola schermata va bene un singolo screen. Scanner: expo-camera / CameraView con lettura QR e gestione permessi secondo l'SDK Expo attuale. Persistenza: @react-native-async-storage/async-storage o alternativa ufficialmente compatibile. Imposta correttamente la descrizione del permesso camera iOS con plugin/config Expo. Controlla che la libreria scanner supporti davvero il comportamento sul dispositivo e documenta eventuali differenze Web. Usa componenti React Native (View, Text, Pressable, TextInput, FlatList) e StyleSheet; evita HTML nel mobile. Niente backend. Comandi attesi: creazione, expo install, expo start, istruzioni per expo run:android e expo run:ios / development build se richiesta. Per la futura build web, configura React Native Web con pacchetti Expo appropriati, produci il comando di export e un elenco di differenze/limiti reali dello scanner in browser; non inventare compatibilità se non verificata.

OUTPUT FINALE RICHIESTO: mostra i file creati/modificati, istruzioni riproducibili, test realmente eseguiti, limiti e punti non verificati. Privilegia la correttezza alla velocità.
